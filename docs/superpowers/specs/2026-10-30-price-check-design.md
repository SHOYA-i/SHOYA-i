# 買い物相場チェックツール 設計書

作成日: 2026-10-30
状態: 設計承認済み（本書のレビュー待ち）

## 1. 目的と前提

スーパーの店頭で、商品の価格が安いかどうかを客観的に判断できるようにする。

| 区分 | 内容 |
|---|---|
| 利用者 | 作成者本人（個人利用） |
| 利用場面 | 店頭でスマホから、数秒で判定を見る |
| 対象 | 食品・日用品が中心 |
| 成功の形 | 商品の価格と内容量を入れると、「安い／普通／高い」と、その根拠（相場との差の％）が分かる |

近隣店舗の価格を網羅した公開APIは確認できなかったため、相場データは次の2つで構成する。

- 公的統計（総務省「小売物価統計調査」、政府統計コード 00200571）
- 自分の購入履歴

近隣店舗との比較は初期スコープに含めない（8章参照）。

## 2. 決定事項

| 項目 | 決定 |
|---|---|
| 相場データ | 公的統計（e-Stat API）＋自分の購入履歴 |
| 店頭の入力 | 手入力（カテゴリ、価格、内容量）から開始。バーコード・写真読み取りは後から追加できる作りにする |
| 判定の軸 | 棚の価格ではなく、基準単位（100g、100ml、1個）あたりの単価 |
| 動かし方 | スマホのブラウザで使うWebアプリ（PWA） |
| 構成 | サーバーなしの静的PWA＋端末内保存（IndexedDB）。公的統計は GitHub Actions が月次で取得し JSON として配信する |
| 配置 | このリポジトリの `price-check/` サブディレクトリ。プロフィール用の `README.md` には触れない |

## 3. 全体構成

```
[月次バッチ: GitHub Actions]
  e-Stat API → 検証 → 単価に整形 → public/data/reference-prices.json

[スマホPWA]
  入力アダプタ → ProductInput → コアロジック
     ├─ 参考値①: reference-prices.json（Service Workerでキャッシュ）
     └─ 参考値②: 購入履歴（IndexedDB）
  → 判定結果の表示 → 「買った」で履歴に保存
```

### 部品と責務

| 部品 | 役割 | 入力 → 出力 | 依存先 |
|---|---|---|---|
| 月次バッチ | e-Stat から品目別価格を取得して整形する | e-Stat API → `reference-prices.json` | アプリケーションID（Secrets） |
| カテゴリ定義 `categories.json` | 画面のカテゴリと e-Stat 品目の対応表。基準単位と系統も持つ | 手で管理 | なし |
| コアロジック | 単価換算、相場との比較、履歴の中央値 | `ProductInput` → 判定結果 | なし（画面・保存先に依存しない純粋関数） |
| 保存層 | 購入履歴の追加・取得、JSONの書き出し・読み込み | 履歴 ⇄ IndexedDB | ブラウザ |
| 画面 | 入力フォーム、結果カード、「買った」ボタン、履歴一覧、設定（地域・閾値） | ユーザー操作 | 上記すべて |
| 入力アダプタ | 入力を共通の `ProductInput` にそろえる。初期は手入力のみ | フォーム → `ProductInput` | なし |

拡張の入口は入力アダプタ。バーコードや写真読み取りを足す場合も、同じ `ProductInput` を返せば、コアロジックと画面は変えない。

## 4. 判定ロジック

### 4.1 単価への換算

- 入力は、税込／税抜の別、価格、内容量、個数。
- 税抜入力は税込に換算する。既定の税率は、飲食料品が8%、それ以外が10%（カテゴリごとに `categories.json` で持つ）。円未満は切り捨てる。
- 内容量の系統は3つ。質量（g・kg）、体積（ml・L）、個数（個・枚・本・袋など）。カテゴリの基準単位（100g、100ml、1個）に換算する。
- 入力の系統がカテゴリの基準系統と合わない場合は、計算せず入力のやり直しを促す。

### 4.2 参考値

| 参考値 | 中身 | 使う条件 |
|---|---|---|
| ① 公的統計 | 設定した地域の、対象月の平均単価。対象月と地域を表示する | 該当品目と該当地域の値がある場合 |
| ② 自分の購入履歴 | 同じカテゴリの直近12か月の単価の中央値（件数が偶数なら中央2件の平均） | 3件以上ある場合 |

設定した地域に値がなく、全国値がある場合は全国値を使う。全国値の有無は未確認（9章）。

### 4.3 判定

- 差の割合 = (今の単価 − 基準単価) ÷ 基準単価。判定は丸める前の値で行い、表示は整数％にする。
- ラベルの基準は、履歴が3件以上あれば②、なければ①。もう一方は参考として併記する。理由は、公的統計が代表銘柄の平均であり、高品質ブランドを買う場合は常に「高い」と出るため。
- 閾値の既定値は、差が−10%以下で「安い」、+10%以上で「高い」、その間は「普通」（境界値を含む）。根拠のある数値ではなく初期案であり、設定で変更できる。
- 結果には、ラベル、単価、各基準との差（％）、基準の出所（対象月、地域、履歴の件数）を表示する。

### 4.4 データが足りないとき

| 状況 | 動作 |
|---|---|
| どちらの参考値もない | 判定を出さず、「相場データなし」と表示する。履歴への保存だけを促す |
| 公的統計だけがある | ラベルを出し、「代表銘柄の平均なので目安です」と注記する |
| 統計の対象月が現在月から3か月以上前 | 古い旨の警告を出す |
| 入力した単価が、いずれかの基準の10倍以上または10分の1以下 | 「この入力で合っていますか？」と確認する。入力は止めない |

## 5. データモデル

### 5.1 購入履歴（IndexedDB）

```ts
type Dimension = 'mass' | 'volume' | 'count';

interface Purchase {
  id: string;            // UUID
  categoryId: string;
  productName?: string;
  taxIncludedPrice: number; // 円
  quantity: number;      // 合計内容量（1パックの内容量 × パック数）。単位は下の unit
  unit: string;          // 'g' | 'kg' | 'ml' | 'L' | '個' など
  unitPrice: number;     // 基準単位あたりの税込単価
  purchasedAt: string;   // ISO 8601 日付
  storeName?: string;    // 将来の店別比較用（初期は任意入力）
  memo?: string;
}
```

### 5.2 `reference-prices.json`

```ts
interface ReferencePrices {
  version: 1;
  generatedAt: string;   // ISO 8601
  source: {
    name: '小売物価統計調査';
    statCode: '00200571';
    creditText: string;  // e-Stat のクレジット表示文言
  };
  items: Array<{
    categoryId: string;  // categories.json と対応
    estatItemCode: string;
    standardBrand: string; // 統計上の基本銘柄の説明
    dimension: Dimension;
    baseUnit: string;    // '100g' | '100ml' | '1個'
    areas: Record<string, { month: string; unitPrice: number }>; // month: 'YYYY-MM'
  }>;
}
```

### 5.3 バックアップ

履歴のJSON書き出し・読み込みを持つ。ファイルには `version` を含める。

## 6. エラー処理

| 場面 | 対応 |
|---|---|
| 月次バッチが失敗（API停止、ID無効、表の形式変更） | 取得結果を書式と件数で検証する。異常なら前回の `reference-prices.json` を残して上書きせず、ワークフローを失敗させる |
| 参考データを読み込めない | 履歴だけで判定を続け、「公的統計が読めません」と表示する |
| 参考データが古い | 更新日を常に表示し、3か月以上前なら警告する |
| 不正な入力（0円、負の値、数値以外） | 入力できないようにする |
| ブラウザが端末内データを消す | 永続化の許可（`navigator.storage.persist()`）を要求する。JSONの書き出しを定期的に促す |
| JSONの読み込み | 形式とバージョンを検証し、件数をプレビューしてから反映する。確認なしの上書きはしない |

データがないときに判定をでっち上げない。

## 7. テスト方針

| 対象 | 方法 |
|---|---|
| コアロジック | 先にテストを書く（TDD）。単価換算、税の扱い、閾値の境界値、中央値、データ不足、単位の不一致を表形式のケースで検証する（Vitest） |
| 月次バッチ | 実際のAPI応答を保存した固定データ（fixture）で整形処理をテストする。CIのテストから実APIは呼ばない |
| 保存層 | `fake-indexeddb` で、追加、取得、書き出し、読み込みの往復を確認する |
| 画面 | Playwright で、スマホ画面幅の「入力→判定→保存→履歴に出る」と、オフラインでの判定を確認する |
| 実機 | ホーム画面への追加と店頭での使い勝手は、作成者のスマホで確認する |

## 8. 技術選定とスコープ

- TypeScript、Vite、Vitest、Playwright。画面は4つ程度なので、UIフレームワークは使わない。
- ホスティングは GitHub Pages（GitHub Actions でデプロイ）を想定する。リポジトリ設定でのPages有効化は作成者が行う。

### 作らないもの

バーコード読み取り、写真読み取り、近隣店舗の価格データ、複数端末の同期、アカウント機能。

## 9. 実装前に確認する事項

ネットワーク制限により、公式ページの本文はまだ読めていない。次の点は、`www.e-stat.go.jp`、`www.stat.go.jp`、API用ホストが許可されてから確認し、本書を更新する。

| 確認事項 | 影響する箇所 |
|---|---|
| 「主要品目の都市別小売価格」の品目数、都市の範囲、更新頻度 | カテゴリ定義、地域設定 |
| 全国値が表に含まれるか | 4.2の地域フォールバック |
| e-Stat の価格が税込か | 4.1の税の扱い |
| API用の統計表ID、リクエスト上限、利用料金の有無 | 月次バッチ |
| 基本銘柄の内容量（例: 卵10個入りなど）の確認 | 単価換算、`standardBrand` |
| 利用スマホでのストレージ消去の挙動 | 6章のバックアップ頻度 |

作成者側で必要な作業は次の2つ。

- e-Stat のユーザー登録とアプリケーションIDの発行（リポジトリの Secrets に登録）。
- GitHub Pages の有効化。

## 10. 実装の順序

1. コアロジックとテスト
2. 保存層
3. 手入力の画面
4. 公的統計の月次バッチ

4は、ネットワークの許可とアプリケーションIDの発行が前提。それまでの画面開発には、「サンプルデータ」と画面にはっきり表示する仮の参考値を使う。これは実データではなく、本番には含めず、バッチが動いた時点で差し替える（承認済み）。
